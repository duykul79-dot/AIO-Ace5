0. Tóm tắt điều hành

Module AIO Ace5 v3.0.3RC là một bộ công cụ Magisk/KernelSU/APatch khá lớn nhắm tới ColorOS 15-16 trên Qualcomm SM8650 (OnePlus Ace 5 / Realme GT-class). Module gói gọn 5 nhóm tính năng: Debloat, Cleanup, Battery analysis, Performance tuning (Game Max / Charge Max / Thermal Shutdown / 360 Hz touch), và Game device-identity spoofing (Zygisk + COPG controller).

Đánh giá tổng thể: chất lượng code khá cao so với mặt bằng các module Magisk Việt hóa — có TOCTOU defense, có path-canonicalization, có singleton lock, có rollback path, có XSS-escape trong WebUI, có gating bằng flag-file để tránh bootloop. Không phát hiện lỗ hổng nghiêm trọng kiểu eval động, command injection, hay path traversal khai thác được. Các phát hiện chủ yếu là medium/low về quality-of-code, dead pattern, vài chỗ POSIX-strict không tuân thủ (nhưng chạy ổn vì Android shell là mksh), và một vài điểm packaging cần dọn.

5. Service lifecycle: post-fs-data.sh / service.sh / uninstall.sh

5.1 post-fs-data.sh

H-01 · Bind-mount stub vào /system/bin/logd ở post-fs-data có rủi ro bootloop
post-fs-data.sh:36-39
bind_file "$STUB_DAEMON" /system/bin/logd
bind_file "$STUB_CMD"    /system/bin/logcat
bind_file "$STUB_DAEMON" /system/bin/update_engine
bind_file "$STUB_CMD"    /system/bin/update_engine_sideload

Phân tích: Cooldown thay logd bằng stub script chạy while sleep 3600. Trên ColorOS, theia_screen_monitor hoặc oppoCar có thể coi việc logd-restart-loop là điều kiện trigger crash report — chuyển sang stub thì các service kia mất kênh log nhưng không panic. Tuy nhiên:

  • Nếu STUB_DAEMON bị xóa (vd. SELinux denial khi tải file ở post-fs phase) thì mount -o bind sẽ fail và logd gốc vẫn chạy → OK.
  • Nếu bind thành công nhưng stub bị mất exec permission (set_perm 0700 trong customize.sh, nhưng nếu ROM remount /data ro thì bind có thể không apply đúng) → logd start thất bại → init có thể restart liên tục → bootloop ColorOS.
  • Gating bằng cooldown_enabled.flag là đúng — chỉ user chủ động bật mới apply.

Khuyến nghị: thêm verify sau bind_file:

bind_file "$STUB_DAEMON" /system/bin/logd
sleep 0.2
if ! /system/bin/sh /system/bin/logd -h >/dev/null 2>&1; then
  umount /system/bin/logd 2>/dev/null
  _log "logd stub verify failed → revert"
fi

(check chỉ là smoke-test, không phải lệnh thật của logd, nhưng nếu shell không exec được thì bind sai → revert ngay).

M-01 · `sleep 1` blocking ở post-fs-data làm chậm boot
post-fs-data.sh:34
for S in logd logd-auditctl ... ; do ctl_stop "$S"; done
sleep 1

1 giây blocking ở post-fs-data là đáng kể (toàn bộ chain sau đó phải đợi). Một số module khác cũng làm vậy nên user có thể không nhận ra, nhưng nếu kết hợp với 3-4 module có cooldown thì delay cộng dồn.

Khuyến nghị: giảm xuống 0.3 (mksh hỗ trợ float sleep) hoặc usleep 300000 nếu busybox có.

L-04 · `_mount_has` parse `mount` không xử lý mount target có khoảng trắng
post-fs-data.sh:16-19, service.sh:31-34, uninstall.sh:18-21
mount | awk -v t="$TARGET" '$2==t{found=1} END{exit !found}'

mount output có format src on target type ...; awk $2 sẽ trả về "on" chứ không phải target. Đây là bug typo phổ biến nhưng thực tế trên Android busybox mount output là src target type ... (không có "on") nên $2 đúng. Tuy nhiên cấu trúc này không portable giữa toybox/busybox.

Khuyến nghị: parse /proc/self/mountinfo hoặc cat /proc/mounts | awk '{print $2}' để robust hơn:

grep -qF " $TARGET " /proc/mounts
M-02 · Disable ColorOS packages không double-check user 0 trước
service.sh:42-46
disable_pkg() {
  PKG="$1"
  pm path "$PKG" >/dev/null 2>&1 || pm list packages -u 2>/dev/null | grep -qx "package:$PKG" || return 0
  pm disable-user --user 0 "$PKG" >/dev/null 2>&1 || pm disable --user 0 "$PKG" >/dev/null 2>&1
}

Hợp lý, nhưng:

  • grep -qx "package:$PKG" sẽ false-negative nếu package có dấu chấm đầu hoặc ký tự đặc biệt (vd. nếu PKG là foo.bar, regex grep -qx dùng fixed string OK).
  • pm list packages -u liệt kê uninstalled packages. Người ta đã uninstall rồi mà module lại disable thêm — vô hại nhưng dư công.

5.2 service.sh

OK · Wait sys.boot_completed có timeout 240s
service.sh:140-146

Pattern wait đúng chuẩn: _boot_max=120 * sleep 2 = max 240s. Magisk init.rc thường kích service.sh ở late_start, system thường boot_completed trong ~30-60s nên 240s là buffer đủ.

M-03 · Log rotate xóa file cũ > 7 ngày, nhưng đếm _i không dùng
service.sh:18-25
_i=0
for _old in /data/local/tmp/aio24_service.log /data/local/tmp/aio25_service_*.log; do
  [ -f "$_old" ] || continue
  _i=$((_i+1))
  _mt=$(stat -c %Y "$_old" 2>/dev/null || printf '0')
  [ $(( $(date +%s 2>/dev/null || printf '0') - _mt )) -gt 604800 ] && rm -f "$_old" 2>/dev/null
done

_i được increment nhưng không dùng cho rotation count. Có vẻ là di sản từ version cũ có giới hạn số file. Không gây bug nhưng dead code.

5.3 uninstall.sh

H-02 · `rm -rf /data/adb/modules/COPG` có thể xóa module bên thứ 3 nếu marker collision
uninstall.sh:14-16, 131
COPG_COMPAT_DIR="/data/adb/modules/COPG"
COPG_COMPAT_MARKER="$COPG_COMPAT_DIR/.aio_owned"
...
[ -f "$COPG_COMPAT_MARKER" ] && rm -rf "$COPG_COMPAT_DIR" 2>/dev/null

Phân tích risk:

  • Marker là một file rỗng tên .aio_owned. Bất kỳ ai (user, module khác, attacker với root) cũng có thể touch /data/adb/modules/COPG/.aio_owned trên một COPG module bên thứ 3.
  • Khi user uninstall AIO Ace5 → script xóa cả module COPG bên thứ 3 → user mất module với 0 cảnh báo.
  • Trong thực tế attack chain hiếm xảy ra (cần root), nhưng accident chain hoàn toàn có thể: nếu user thử nghiệm với COPG xen kẽ AIO Ace5 nhiều lần, marker có thể tồn tại từ session trước.

Khuyến nghị:

  1. Marker nên là file có nội dung chứa checksum hoặc version, vd. aio_ace5_v303rc_copg_owned_$(date +%s).
  2. Check thêm module.prop của COPG dir: nếu id != COPG_AIO_SHIM thì không xóa.
  3. Hoặc đơn giản: chỉ rm -f các file con AIO biết, không rm -rf cả dir.
OK · Backup restore qua `debloat_backup.list`
uninstall.sh:63-68

Đọc lại danh sách package đã debloat và pm enable lại từng cái. Đây là pattern best-effort đúng đắn — không bao giờ guarantee restore (vì user có thể đã clear /data) nhưng cố gắng hết sức.

L-05 · Setprop revert ở uninstall không match số lượng đã set ở post-fs-data
uninstall.sh:96-108 vs post-fs-data.sh:45-67

post-fs-data set 22 prop khác nhau; uninstall.sh chỉ revert 13. Các prop chưa revert: persist.sys.preload, persist.sys.monitor, persist.sys.hotstart, persist.sys.fflag.override.settings_enable_monitor_phantom_procs, vài prop OPlus theia/screen_monitor, v.v. Sau uninstall + reboot, các prop này vẫn còn ở giá trị đã setprop.

Lưu ý: các persist. prop sẽ tồn tại qua factory reset nếu /data/property không bị wipe. Một số prop khác như sys.oplus.respreload.vipcsdk.enabled chỉ là runtime → tự reset sau reboot.

M-12 · Shutdown thermal disable: rủi ro hardware cao dù có 2-step arm/confirm

Rủi ro thực:

  • Bản chất feature là bind overlay high_temp để vô hiệu/giảm logic thermal shutdown của ROM. Nếu payload generated sai (parsing XML lệch, schema mới), kernel vẫn shutdown nhưng userspace nghĩ đã disable → false confidence.
  • Nếu bật lâu dài, máy mất safety net cuối cùng để tự ngắt khi quá nóng → có thể hại pin, hại die SoC, hoặc gây thermal-runaway trong game session dài.
  • Flag persistent qua reboot (không auto-expire). User có thể quên đã bật.

Khuyến nghị: (a) mặc định OFF + cảnh báo UI rõ hơn (đã có một phần); (b) auto-expire flag sau N phút sử dụng hoặc sau 1 reboot — nếu user vẫn muốn dùng thì arm lại; (c) thêm watchdog kiểm tra temp sensor: nếu >= 50°C trong >= 30s thì tự bỏ disable.

13.2 Cross-cutting concerns

INFO · Sử dụng `/system/bin/sh` (mksh) thay vì busybox sh nhất quán

Mọi shebang đều là #!/system/bin/sh. Đây là mksh trên Android — hỗ trợ read -t, hỗ trợ [[ ]], hỗ trợ arithmetic $((...)). Module tránh được nhiều vấn đề POSIX strict.

INFO · Nhất quán xử lý lỗi & log

Mọi script đều có set +e (không exit on error) → khả năng tự rollback và log lý do thất bại từng bước. Tradeoff: lỗi silent hơn, nhưng user thấy progress đến cuối thay vì abort giữa chừng.

INFO · Flag-file gating chống bootloop

Mọi feature persistent (cooldown, game_max, charge_max, touch360, thermal_shutdown_disable, game_spoof) đều gate bằng flag-file trong $MODPATH/bin/*.flag. customize.sh xóa các flag khi update → safe-by-default sau update.

INFO · Tránh hardcode đường dẫn user

Hầu hết script dùng readlink -f "$0" để self-locate → không phụ thuộc ID module hardcoded. Exception duy nhất: game_spoof_config.json:25 có path leak (M-04).

INFO · Không có unit test / sandbox test

Module không kèm test suite. Mỗi thay đổi phải test thủ công trên thiết bị thật. Đây là chuẩn cho module Magisk nhưng đáng note.
